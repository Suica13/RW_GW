# BattleUniverse 历史原因与不可随意简化项

> 本清单用于记录项目中部分“表面上显得多余、复杂或可以直接简化”的结构为何存在。  
> 很多实现并不是理想架构，而是为了绕过《铁锈战争》脚本限制、支持复杂机制、兼容多个 DLC，并规避已知引擎问题形成的。
>
> 在没有理解原始目的、完成等价测试之前，请不要仅以“代码太绕”为理由直接删除或合并相关流程。

---

## 1. 建造列表没有全部直接写在工厂中

### 表面上看

普通 MOD 通常只需要在工厂中加入类似内容：

```ini
canBuild_Tank
```

或者直接将某个单位添加到固定建造列表中。

### 历史原因

BattleUniverse 的建造权限不只取决于工厂本身，还可能受到以下条件影响：

- 当前剧本；
- 当前阵营；
- 当前科技等级；
- 已解锁科技；
- 全局队伍 Tag；
- DLC 是否加载；
- 多个 DLC 是否混合加载；
- 特殊模式或开局设置；
- 建筑是否已经转换为对应阵营版本。

因此，建造列表被拆分为注册、接收、条件判断和实际显示等多层逻辑，用来支持比普通 `canBuild` 更复杂的扩展条件。

### 不可直接简化为

```ini
canBuild_Tank
```

否则可能导致：

- 未解锁科技提前出现；
- 错误阵营能够生产该单位；
- 未安装对应 DLC 时出现非法引用；
- 混合 DLC 时读取错误单位；
- 后续无法继续扩展建造条件。

---

## 2. 单位无法完全作为独立 INI 编写

### 表面上看

其他 MOD 的单位通常可以独立完成，只需要由工厂引用即可。

### 历史原因

BattleUniverse 中的单位可能同时依赖：

- 驾驶员系统；
- 阵营标签；
- 科技树；
- 工厂注册；
- ACE 或特殊单位条件；
- 模式管理单位；
- DLC 公共模板；
- Main 包中的公共逻辑；
- 同名占位单位或转换单位。

因此，一个单位是否能够正常生成、显示和使用，不一定只由该单位自己的 INI 决定。

### 维护注意

单位出现问题时，不能只检查单位本体。还需要检查：

- 工厂注册；
- 科技节点；
- 阵营 Tag；
- Get/Send 逻辑；
- UnitList 或公共列表；
- DLC 与 Main 的对应关系。

---

## 3. 同名占位单位与 `convertTo` 机制

### 表面上看

Main 包和 DLC 中出现同名单位，或者先生成一个占位单位再转换为正式单位，看起来属于重复设计。

### 历史原因

Main 包需要在不知道某个 DLC 是否存在的情况下，提供稳定的公共入口。

因此先由 Main 提供占位单位，再由已加载的 DLC 使用同名正式单位或 `convertTo` 接管后续逻辑。

这种方式可能用于：

- 避免 Main 直接引用不存在的 DLC 单位；
- 支持 DLC 可选加载；
- 支持多个 DLC 混合；
- 让公共模式选择界面始终能够工作；
- 在确定 FactionIndex 后转换为正确阵营 HQ；
- 在转换过程中挂载对应科技树。

### 不可直接删除占位单位

删除或改名可能导致：

- DLC 未加载时出现非法引用；
- HQ 无法转换；
- 科技树无法挂载；
- 场景或阵营选择按钮失效；
- 混合 DLC 兼容性被破坏。

---

## 4. 使用单位承担管理器和信息传递职责

### 表面上看

项目中存在一些没有普通战斗用途的单位，只负责保存状态、触发 Action、传递资源或修改 Tag。

### 历史原因

《铁锈战争》的 MOD 脚本没有提供正常游戏引擎中的：

- 全局管理器；
- ScriptableObject；
- 服务类；
- 事件总线；
- 独立状态机；
- 可自由访问的全局数据对象。

因此只能使用隐藏单位、附件单位、占位单位或特殊建筑模拟管理器。

这些单位实际上可能承担：

- 保存模式设置；
- 保存 FactionIndex；
- 广播开局参数；
- 接收其他单位发送的信息；
- 修改全局队伍 Tag；
- 驱动科技树；
- 驱动建筑转换；
- 触发下一阶段流程。

### 维护注意

不能因为某个单位“没有模型”或“不能战斗”就认定它没有用途。

---

## 5. 使用 Tag 和 Resource 传递状态

### 表面上看

同一项信息可能同时出现在单位 Tag、全局队伍 Tag、Resource 和 Action 条件中，看起来重复且耦合严重。

### 历史原因

不同脚本功能能够读取的数据范围不同。

某些条件只能读取：

- 自身 Tag；
- 队伍全局 Tag；
- 自身 Resource；
- 附件单位；
- 特定范围内的其他单位。

因此，同一状态可能需要被转换或同步为不同形式，才能被不同系统读取。

例如：

```text
FactionIndex
→ HQ 转换
→ 添加阵营 Tag
→ 科技树读取 Tag
→ 建筑槽读取 Tag
→ 工厂根据 Tag 开放单位
```

### 不可随意合并

看起来含义相近的 Tag 或 Resource，不一定能互相替代。删除其中一个可能导致某个特定系统无法读取状态。

## 6. 使用 Step1、Step2、Step3 分阶段生成单位

### 表面上看

生成三个单位时，本可直接写成：

```ini
spawnUnits: Tank*3
```

但项目中可能使用：

```text
Step1
→ 生成第一个单位
→ Step2
→ 生成第二个单位
→ Step3
→ 生成第三个单位
```

### 历史原因

《铁锈战争》在同一时刻或同一 tick 内多次读取随机数时，可能得到相同的 `rnd` 结果。

如果三个单位在同一时刻生成，并且驾驶员属性依赖随机数，可能导致：

- 三名驾驶员拥有完全相同的属性；
- 随机等级相同；
- 随机技能相同；
- 其他由 `rnd` 决定的数据完全重复。

通过 Step1、Step2、Step3 将生成操作错开，可以让每次生成在不同时间重新计算随机数。

### 不可直接简化为

```ini
spawnUnits: Tank*3
```

除非已经确认所有随机驾驶员属性均能独立重新取值。

### 建议注释

```ini
# [ENGINE_WORKAROUND]
# [DO_NOT_SIMPLIFY]
# 同一 tick 中多次读取 rnd 可能得到相同结果。
# 必须分阶段生成，避免同批驾驶员属性完全一致。
```

## 7. 多层 Action 不一定是无意义跳转

### 表面上看

某些流程可能连续触发多个 Action，而每个 Action 只执行少量操作。

### 历史原因

拆分 Action 可能用于：

- 错开执行时间；
- 等待单位生成完成；
- 等待 Tag 或 Resource 更新；
- 避免同一 tick 的随机数重复；
- 让附件先完成挂载；
- 让 `convertTo` 完成后再执行后续逻辑；
- 将复杂条件拆开，绕过单个条件表达式限制；
- 便于不同 DLC 覆盖其中某一步。

### 维护注意

合并 Action 前，需要确认它们是否依赖执行顺序或时间差。  
能够写在同一段代码中，不代表可以在同一个 tick 中执行。

---

## 8. 科技树必须通过 HQ 或附件单位挂载

### 表面上看

科技树似乎可以直接作为独立 UI 或直接放入玩家列表中。

### 历史原因

当前结构需要在阵营确定后，才能知道应该加载哪个科技树。

因此一般流程为：

```text
选择阵营
→ 写入 FactionIndex
→ HQ 检测 FactionIndex
→ 转换为正式阵营 HQ
→ 添加科技树 Core 附件
→ 科技树根据阵营 Tag 显示内容
```

如果跳过 HQ 转换或附件挂载，可能出现：

- 科技树 UI 不显示；
- 显示错误阵营科技；
- 科技节点无法取得阵营状态；
- DLC 未加载时出现非法引用。

---

## 9. BuildingSlot 需要按场景或阵营转换

### 表面上看

所有阵营似乎可以共用同一个建筑槽。

### 历史原因

建筑槽需要知道当前加载的是哪个剧本、哪个阵营以及哪些 DLC。

因此建筑槽可能需要根据 FactionIndex 或 Tag 转换为：

- 0079 建筑槽；
- 0087 建筑槽；
- SEED 建筑槽；
- 对应阵营的特定建筑槽。

转换后，建筑槽才能读取正确的：

- 可建造建筑；
- 工厂列表；
- 科技条件；
- 阵营专属建筑；
- DLC 资源。

### 不可只修改单个 DLC

公共建筑槽模板或转换逻辑如果发生变化，可能需要同步到其他包，以保证混合 DLC 加载时逻辑一致。

---

## 10. 公共逻辑分布在 Main 与多个 DLC 中

### 表面上看

相似逻辑在多个包中重复存在，似乎应该只保留一份。

### 历史原因

不同 DLC 可能单独加载，也可能与其他 DLC 混合加载。

同时，某些引用只有在对应 DLC 已存在时才合法。为了避免加载不存在的单位，公共逻辑不得不拆分为：

- Main 提供公共入口和占位内容；
- DLC 提供正式实现；
- 各 DLC 保留自己的转换或注册逻辑；
- 部分公共模板需要复制并针对当前 DLC 调整。

### 维护注意

修改 `Mod`、公共模板、BuildingSlot、StrategicLocation 等内容时，需要确认是否必须同步其他 DLC。

---

## 11. 无法通过报错快速定位非法引用

### 表面上看

只要按照模板复制并修改名称，新增 DLC 应该不难。

### 历史原因

当一个 INI 引用了非法单位、路径或其他 INI 时，引擎可能只输出一整条难以阅读的错误信息，无法清楚显示完整调用链。

因此一个错误可能来自：

- 当前文件；
- `copyFrom` 的文件；
- 被引用单位；
- 附件单位；
- `convertTo` 目标；
- Action 间接触发的单位；
- 其他 DLC 中的同名模板；
- 未同步的公共逻辑。

### 维护建议

排错时应分阶段启用内容：

1. 先确认目录和单位本体可加载；
2. 再加入 `copyFrom`；
3. 再加入 Action；
4. 再加入附件；
5. 再加入科技树和工厂注册；
6. 每增加一层后立即启动测试。

不要一次性复制完整阵营后再统一排错。

## 12. 重复注册可能是为了支持复杂条件

### 表面上看

单位信息在 Tech、Factory、Common、BuildSlot 等多个位置重复注册，似乎属于低效设计。

### 历史原因

这些注册位置可能分别负责：

- 声明单位存在；
- 将单位发送给建筑；
- 判断科技是否解锁；
- 判断阵营是否匹配；
- 判断 DLC 是否加载；
- 将单位加入实际按钮列表；
- 控制 UI 是否显示；
- 处理混合 DLC 下的覆盖关系。

因此，它们可能不是完全相同的重复代码，而是同一条流程上的不同阶段。

---

## 13. FactionIndex 不是普通编号

### 表面上看

FactionIndex 只是一串难以阅读的数字，似乎可以随意重新编号。

### 历史原因

FactionIndex 的不同位可能用于表示：

- 世界观或系列；
- 剧本；
- 阵营；
- 阵营内部的不同可能性。

例如：

```text
10 / 20 / 10 / 1
世界观 / 剧本 / 阵营 / 可能性
```

不同系统可能通过完整值或部分范围判断：

- 当前场景；
- 当前阵营；
- 应转换到哪个 HQ；
- 应使用哪个 BuildingSlot；
- 应加载哪个科技树。

### 维护注意

新增编号前需要检查是否与现有值重复，并确认所有依赖该编号的转换条件已经同步。

---

## 14. 结构复杂并不代表所有复杂度都能被消除

### 历史背景

该项目经历过多次持续扩展：

```text
独立单位
→ 阵营
→ 科技树
→ 多剧本
→ 多 DLC
→ DLC 混合加载
→ 驾驶员随机属性
→ 更复杂的建造条件
```

《铁锈战争》的脚本能力并未随项目规模增长，因此很多系统只能依靠单位、Action、Tag、Resource 和 `convertTo` 模拟。

部分结构经过重构后仍然复杂，不一定是重构失败，而可能是引擎限制下无法继续降低的必要复杂度。

# 维护者基本原则

遇到看起来可以简化的结构时，先确认以下问题：

1. 它是否用于错开 tick？
2. 它是否用于重新计算随机数？
3. 它是否用于避免引用未加载 DLC？
4. 它是否用于混合 DLC 兼容？
5. 它是否负责在 Tag、Resource 和单位之间传递状态？
6. 它是否是科技树、HQ 或 BuildingSlot 的入口？
7. 它是否允许以后增加更复杂的判断条件？
8. 简化后是否只测试了“能生成”，却没有测试属性、科技、阵营和 DLC 状态？
9. 是否已经全文搜索该单位名、Action 名、Tag 和 FactionIndex？
10. 是否保留了可回退版本？

# 建议使用的代码注释标签

```ini
# [ENGINE_WORKAROUND]
# 因引擎行为或限制产生的绕行方案。

# [DO_NOT_SIMPLIFY]
# 表面可以缩短，但简化会改变实际行为。

# [CROSS_DLC]
# 修改后需要检查或同步其他 DLC。

# [ORDER_DEPENDENT]
# 必须保持当前执行顺序。

# [TICK_DEPENDENT]
# 依赖跨 tick 执行，不可合并到同一时刻。

# [RANDOM_DEPENDENT]
# 与 rnd 重新计算或随机属性生成有关。

# [PLACEHOLDER]
# Main 或公共包中的占位内容，由 DLC 正式内容接管。

# [HIDDEN_DEPENDENCY]
# 依赖关系没有直接写在当前文件中，需要全文搜索。

# [LEGACY_REASON]
# 历史兼容逻辑，删除前必须确认旧内容和混合 DLC 不再依赖。
```

# 当前已确认的典型案例

## 分阶段生成驾驶员

```text
直接生成 Tank*3
→ 三次 rnd 在同一时刻取值
→ 三名驾驶员随机属性完全相同
```

当前处理：

```text
Step1 生成第一个
→ Step2 生成第二个
→ Step3 生成第三个
```

目的：通过错开生成时间，使每名驾驶员重新取得随机属性。

## 复杂建造列表

```text
直接 canBuild
```

无法满足阵营、科技、DLC、模式和扩展条件。

当前处理：

```text
公共注册
→ 条件判断
→ Tag/Resource 传递
→ 科技解锁
→ 工厂接收
→ 实际显示建造按钮
```

目的：让建造列表能够支持复杂条件及后续扩展，而不是只能静态绑定单位。
